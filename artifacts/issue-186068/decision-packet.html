Concrete contract proposals — NOT accepted or implemented

  1. Host profile + audience owners: separate selection from delivery. Preserve selectedProfileId exactly. Evaluate whether that selected overlay is admitted to the current audience separately. Recommended first-stage group behavior: deliver shared defaults only unless an explicit accepted audience-admission contract permits more; never silently substitute the sender's profile. A Bob-authenticated edit in an Alice-assigned session edits Bob's file while leaving Alice as the selected profile. If Alice's profile is not admitted for that audience, omit it rather than selecting Bob. This delivery restriction changes existing behavior and requires upstream acceptance before coding.
  2. Knowledge + host authority owners, in #186067: person/shared grants. The host binds authenticated canonical person, actual conversation audience, agent ceiling, admitted shared spaces, and current authority lifetime. Knowledge consumes that trusted grant and uses its existing publication/access owners for both reads and writes. The selected personalization profile is never the private Knowledge principal. A caller-provided person/record/history ID is a locator, not a grant. Recheck current grants before releasing records AND titles, counts, IDs, evidence, revisions, graph paths, and cached results. Revocation/restart must not restore old authority. Define the public contract there, not a parallel grant/profile registry in this issue.
  3. LosslessClaw + host context owners: history and delegation. Define and qualify the supported expansion API's audience checks, including explicit history IDs, delegated expansion, membership changes, and previously delivered history. Use supported host/plugin APIs only. A Knowledge search pass must not certify LCM expansion. Recommend fresh fixture conversations first; existing private-bearing history remains unqualified until its owner defines safe handling, without silent deletion or rewriting by Knowledge.
  4. Host filesystem/sandbox + harness owners: choose the support boundary. Recommended bounded first stage: qualify a tool/mount profile in which raw read/list/write/edit/apply_patch/shell/native filesystem paths cannot reach non-admitted profile, Knowledge, evidence, or history roots. Use existing tool and sandbox owners, not a special-case Knowledge path filter. If such confinement is unavailable for a combination, label that combination unsupported for this privacy claim or refuse its qualification. Do not claim unrestricted shared-root shell access is safe. Separate Gateways/OS identities remain the recommendation for mutually untrusted users, not a new promise from this issue.
  5. Knowledge + host personal-file owners: inferred views are data, never instructions. Keep inferred models in existing Knowledge records with source restrictions and lifecycle. No inference/scribe/recall process promotes them into USER.md or invokes self-service editing. USER.md changes remain explicit authenticated-user edits via the canonical owner. User-authored directives retain precedence; conflicting inferences are not silently treated as amendments. Existing tool wording says to edit only when asked; that wording alone is not a hard intent-separation proof against all writable tools. Upstream owners must accept the enforcement/support boundary before implementation.

No new schema, permission, configuration, SDK, retention, or filesystem contract was implemented. These proposals are deliberately owner-scoped decisions, not an invented accepted API.
